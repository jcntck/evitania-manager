# ADR-002: Use Scalable Relational Selection with Inline Creation

## Status

Accepted

## Date

2026-07-25

## Context

Simple selects become unusable as the catalog grows. Users also lose context
when a required item or product is missing while they are editing a recipe,
smelting process, resource, monster, or boss.

## Decision

Every relational field provides searchable selection and inline creation of
eligible related records. Opening inline creation preserves the parent form;
successful creation returns to it and selects the new record automatically.
Recipe and smelting component fields allow multiple records to be selected in
one action, followed by an independently editable positive integer quantity for
each component.

## Alternatives Considered

### Alternative 1: Separate CRUD flows only

- **Description**: Users leave the parent form to create dependencies.
- **Pros**: Fewer nested flows.
- **Cons**: Loses context and makes catalog construction repetitive.
- **Why rejected**: It does not address the explicit backlog requirement.

### Alternative 2: Shared quantity for a multi-selection

- **Description**: Apply one quantity to all selected components.
- **Pros**: Faster when quantities happen to match.
- **Cons**: Produces accidental data and requires correction in common recipes.
- **Why rejected**: The user selected per-component quantities.

## Consequences

### Positive

- Large catalogs remain searchable.
- Users can build dependency chains without losing unsaved parent work.

### Negative

- Nested cancellation and validation states require clear feedback.

### Risks

- Repeated submission can create duplicates; names and active submissions must
  be validated and duplicate actions must not create duplicate records.

## Implementation Notes

Control and state-management choices belong to the TechSpec.
