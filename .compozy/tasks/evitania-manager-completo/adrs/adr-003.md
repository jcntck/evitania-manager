# ADR-003: Combine Objective Trees with a Consolidated Priority Plan

## Status

Accepted

## Date

2026-07-25

## Context

Players need both an understandable production chain and an actionable combined
shopping/farming list. Shared stock cannot be deducted independently in each
tree because that would spend the same unit more than once.

## Decision

The planner provides an expandable production tree for each objective and an
alternate consolidated list for all pending objectives. A single persistent
global stock is allocated by objective priority; users can reorder objectives.
Each raw item has one active source for the whole plan, selected explicitly when
alternatives exist. Completing a consolidated need credits its current missing
quantity to stock through a reversible recorded action. Completing an objective
is a separate reversible state that removes only that objective from pending
totals.

## Alternatives Considered

### Alternative 1: One consolidated tree

- **Description**: Merge every objective into one dependency tree.
- **Pros**: One visualization.
- **Cons**: Obscures which objective caused a requirement.
- **Why rejected**: The user selected per-objective trees and a consolidated list.

### Alternative 2: Stock per objective

- **Description**: Maintain independent stock values for each goal.
- **Pros**: No allocation priority.
- **Cons**: Duplicates inventory and diverges from the player's real holdings.
- **Why rejected**: The user selected global persistent stock.

### Alternative 3: Proportional stock allocation

- **Description**: Split insufficient stock among objectives.
- **Pros**: Treats objectives symmetrically.
- **Cons**: Produces less actionable partial progress.
- **Why rejected**: The user selected explicit objective priority.

## Consequences

### Positive

- Totals never double-spend stock.
- Users can understand dependencies and act on a concise combined plan.
- Completion remains reversible when plans change.

### Negative

- Reordering objectives can change per-objective missing quantities.
- Reversible stock credits require visible provenance.

### Risks

- A stock credit may conflict with later manual stock edits; reversal removes
  only the recorded credit and must explain any impossible transition.

## Implementation Notes

The TechSpec must define deterministic allocation and recalculation without
changing the product semantics above.
