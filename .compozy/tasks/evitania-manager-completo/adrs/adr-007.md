# ADR-007: Modularize the Renderer without a UI Framework

## Status

Accepted

## Date

2026-07-25

## Context

The renderer is one imperative class that replaces HTML strings. The complete
scope adds nested drafts, searchable multi-selection, focus restoration,
objective ordering, two planner views, and large interactive trees.

## Decision

Keep TypeScript, Vite, native DOM, semantic HTML, and delegated events. Split the
renderer into an application store plus focused modules for navigation, catalog
lists, editor/modal stack, relation picker, objective list, production trees,
consolidated table, notifications, and formatting. Each module owns a DOM root,
renders from immutable view state, and emits typed application actions. Drafts
live outside generated markup so nested creation and cancellation cannot erase
the parent draft.

## Alternatives Considered

### Alternative 1: React

- **Description**: Rewrite the renderer as a React application.
- **Pros**: Mature component, state, and test ecosystem.
- **Cons**: New runtime and concepts for behavior that native modules can cover.
- **Why rejected**: The user selected modular native DOM.

### Alternative 2: Preserve the monolithic renderer

- **Description**: Add every feature to `ApplicationView`.
- **Pros**: Minimum file movement.
- **Cons**: Entangles state, markup, events, validation, and persistence.
- **Why rejected**: It is not testable or maintainable at the required scope.

## Consequences

### Positive

- Existing stack remains small while module boundaries become testable.
- Nested forms and focus behavior have explicit state ownership.

### Negative

- The project must implement small component lifecycle conventions itself.

### Risks

- Ad hoc module conventions can drift; shared `ViewModule`, `AppAction`, and
  render/focus rules must be defined before feature modules.

## Implementation Notes

No runtime UI framework, virtual DOM, or global mutable DOM query contract is introduced.
