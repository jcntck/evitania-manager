# ADR-004: Keep User Data and Managed Assets Local-First

## Status

Accepted

## Date

2026-07-25

## Context

The desktop application must work without a service or account. Installed
application directories may be read-only, while imported images and catalog
data must remain writable and discoverable.

## Decision

All catalog data, plans, stock, preferences, completion records, and imported
images remain usable offline and persist in the application's user-data area.
Managed images are organized as `assets/<module>/` within that area. “Open data
location” reveals the containing location. “Synchronize” is visible but
disabled until a future Google Drive capability is specified.

## Alternatives Considered

### Alternative 1: Store assets in the installation directory

- **Description**: Interpret `./assets/` literally relative to the executable.
- **Pros**: Mirrors the source-tree path.
- **Cons**: Often unwritable and mixes application binaries with user data.
- **Why rejected**: The user selected the managed user-data area.

### Alternative 2: Require a user-selected folder

- **Description**: Ask for a storage location on first run.
- **Pros**: Maximum user control.
- **Cons**: Adds onboarding friction and invalid-path failure modes.
- **Why rejected**: Automatic local storage with a reveal action is sufficient.

## Consequences

### Positive

- Core workflows work offline and survive application restarts.
- User-managed content is separated from replaceable application files.

### Negative

- Users must use the reveal action to locate managed files.

### Risks

- Direct external file modification can corrupt data; invalid data must be
  rejected safely without destroying the last valid state.

## Implementation Notes

The persistence technology and exact operating-system locations belong to the
TechSpec.
