# ADR-009: Keep the Preload Contract Snapshot-Based and Result-Typed

## Status

Accepted

## Date

2026-07-25

## Context

The renderer requires load, save, managed-image, and folder operations. Exposing
one native command per domain edit would duplicate validation and enlarge the IPC
surface, while throwing arbitrary errors makes recovery behavior inconsistent.

## Decision

Expose a frozen `DesktopApi` with four narrow operations: load a
`VersionedSnapshot`, save a complete snapshot with `expectedRevision`, import an
image for an allowlisted category, and open the data directory. Each operation
returns a discriminated `Result<T, DesktopError>` with an allowlisted error code.
IPC handlers validate exact payload shapes in the main process. No generic invoke,
filesystem path, shell command, or raw Electron object crosses the bridge.

## Alternatives Considered

### Alternative 1: Granular domain commands

- **Description**: Expose separate create/update/delete commands per entity.
- **Pros**: Smaller payloads and command-level transactions.
- **Cons**: Large IPC surface and duplicated application rules.
- **Why rejected**: The user selected full-snapshot persistence with revision control.

### Alternative 2: Hybrid snapshot and command API

- **Description**: Use snapshots plus commands for selected operations.
- **Pros**: Flexibility.
- **Cons**: Two mutation models and ambiguous ordering.
- **Why rejected**: It adds complexity without a required use case.

## Consequences

### Positive

- The native attack surface remains small and auditable.
- Renderer recovery behavior is exhaustive over known error codes.

### Negative

- Every save transfers the full in-memory aggregate.

### Risks

- Oversized or hostile IPC values can consume resources; payload validation
  applies configured size and collection bounds before domain processing.

## Implementation Notes

Channel names remain explicit constants shared only as types and values compiled
into main/preload; the renderer receives methods, never channel strings.
