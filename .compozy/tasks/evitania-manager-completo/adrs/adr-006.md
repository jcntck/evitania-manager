# ADR-006: Evolve the Local JSON Aggregate with Revisions and Migrations

## Status

Accepted

## Date

2026-07-25

## Context

Version 0.2.3 persists one `AppData` JSON aggregate. The complete product remains
single-user and local-first, but it needs schema evolution, first-run seed data,
corruption recovery, atomic updates, and detection of stale writers.

## Decision

Keep a single JSON aggregate in the Electron user-data directory. Wrap domain
data in a storage envelope containing `schemaVersion` and monotonic `revision`.
Load performs validated incremental migrations, falls back to a validated backup
when the primary is corrupt, and initializes a packaged seed only when no data
or backup exists. Save uses compare-and-swap against `expectedRevision`, validates
the complete next snapshot, writes and syncs a temporary file, rotates a validated
backup, atomically replaces the primary, and returns the next revision.

The v1 migration adds existing `completedEntities` values to stock and creates
equivalent reversible completion-credit records.

## Alternatives Considered

### Alternative 1: SQLite

- **Description**: Normalize the aggregate into relational tables and transactions.
- **Pros**: Native constraints, granular queries, and transactional writes.
- **Cons**: Native dependency and packaging complexity with little benefit for
  one local aggregate loaded into memory.
- **Why rejected**: The user selected versioned JSON.

### Alternative 2: Unversioned last-write-wins JSON

- **Description**: Preserve the v0.2.3 persistence contract.
- **Pros**: No migration work.
- **Cons**: Silent data loss, no safe evolution, and empty-state fallback on corruption.
- **Why rejected**: It cannot satisfy the PRD integrity and concurrency behavior.

## Consequences

### Positive

- Existing code and user data have a bounded migration path.
- The application remains dependency-light and fully offline.
- Stale saves and corrupt primaries cannot silently replace valid data.

### Negative

- Every write serializes and validates the complete aggregate.
- Migration functions and backup semantics become permanent contracts.

### Risks

- Process crashes around file replacement can differ by operating system; fault
  injection tests must cover each write stage and recovery order.

## Implementation Notes

The Electron process uses `requestSingleInstanceLock()` to prevent ordinary
second application instances. Revision checks still protect against stale
windows and external file replacement.
