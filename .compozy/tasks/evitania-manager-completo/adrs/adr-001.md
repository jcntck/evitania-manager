# ADR-001: Treat `.ai/` as the Product Baseline

## Status

Accepted

## Date

2026-07-25

## Context

Evitania Manager v0.2.3 implements part of the desired product, but the current
behavior, documentation, and release flow diverge from requirements in `.ai/`.
The product also needs useful data on first use without preventing players from
correcting or extending a changing Early Access game catalog.

## Decision

The complete content of `.ai/ideia.md`, `.ai/backlog.md`,
`.ai/data/models.md`, and `.ai/modules/*.md` is the authoritative product
baseline. Existing v0.2.3 behavior may be reused only when it conforms to that
baseline and this PRD. The application ships with an editable initial catalog
derived from valid project data, including `docs/base-cadastro.xlsx` where its
records can be mapped unambiguously.

## Alternatives Considered

### Alternative 1: Preserve v0.2.3 as the authority

- **Description**: Limit the work to incremental backlog fixes.
- **Pros**: Less rework and lower migration effort.
- **Cons**: Preserves known requirement and release inconsistencies.
- **Why rejected**: The requested outcome explicitly permits replacing existing
  work to implement all requirements under `.ai/`.

### Alternative 2: Start with an empty catalog

- **Description**: Require every user to create all game records.
- **Pros**: Avoids stale bundled data.
- **Cons**: Delays first value and recreates spreadsheet setup work.
- **Why rejected**: The user selected a populated, editable starting catalog.

## Consequences

### Positive

- One product baseline resolves conflicts with the current implementation.
- Users can plan immediately and correct changing game data locally.

### Negative

- Existing data and behavior require conformance review and possible migration.
- Seed data must be validated before inclusion.

### Risks

- Early Access changes can make initial records stale; all catalog records remain
  editable and the application must never represent estimates as guarantees.

## Implementation Notes

Technology and migration design are deferred to the TechSpec. Ambiguous
spreadsheet rows must be omitted rather than guessed.
